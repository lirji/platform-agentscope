# DAG 优化执行计划

## 目标、授权与基线

用户 2026-10-14 授权按建议出计划并开始执行。以 `4c5f673` 为基线，在原目录 `refactor/dag-orchestration` 连续实施并正常 Git 交付。
530 项基线测试、Ruff 和 Mypy 通过。应用层自建 DAG，AgentScope 仅在基础设施适配层；Java 中央任务服务继续拥有持久任务状态。

## 问题与设计取舍

- P1：失败节点继续喂给下游，且文本丢失 stopReason；优化模式按失败依赖跳过下游，结果显式携带状态。
- P1：汇总复用带工具 runner；优化模式用已有 TextGenerator 无工具汇总，工具授权由 RunContext 允许列表与 ToolPolicy 双重执行。
- P2：整层屏障及 worker-start 提前；依赖就绪后立即调度，槽位获得后才开始，保留稳定拓扑结果排序。
- P1：单节点预算可被 DAG 倍增；整次运行截止时间覆盖规划/执行/评审，模型调用预算在实际模型边界实施，复用已有中央租户 token 权威。
- P2：Critic 只看到答案；增加节点状态/工具证据，必需节点失败禁止以高分覆盖。
- P2：重规划重跑全部节点；只复用同一次调用内、TTL 内、相同任务及传递依赖输入的成功只读结果，不跨租户或跨请求缓存。
- P2：无节点级持久恢复；S6 单独记录中央契约与演练前置条件，禁止用进程内缓存宣称崩溃恢复。

保留旧模式为默认；通过 `AGENT_DAG_OPTIMIZATION_ENABLED=true` 启用新模式。不新增模型/数据库/消息队列依赖，不修改 Java 领域服务或生产路由。通用优化 DAG 仅开放服务端固定只读工具；Process 保留已有确认/幂等退款入口，不允许重规划重放写操作。

|---|---|---|---|

| S3 | IN_PROGRESS | 整次截止时间，模型调用/保守 token 预留上限，覆盖 Planner/ReAct/Critic/Replan；超限失败关闭 | 并发预算拒绝、取消、规划耗时、租户隔离测试；既有中央日配额继续生效 |
| S4 | READY_AFTER_S3 | 证据评审、确定性失败门禁、TTL 内只读节点复用与依赖变化失效 | 相同任务复用、变化下游重跑、过期/失败/写操作不可复用测试 |

| S6 | CONDITIONAL | 节点级持久恢复 | 中央 DB 所有者、版本化 API、lease epoch 原子检查、输入与版本绑定、结果保留及恢复演练具备后实施 |

S6 是原建议中“长任务再补”的条件能力。当前没有跨服务节点恢复契约及长任务成本证据；本轮产出恢复设计与前置条件，不扩仓实现或新增第二任务权威。条件不满足不能标记 S6 已实现。

## 兼容与验证边界

外部 HTTP/JSON 字段保持不变；新模式 stopReason 使用现有字符串字段表达 SKIPPED/PARTIAL。
未知依赖在旧模式继续忽略，新模式拒绝，避免漏依赖；这是显式配置下的 BEHAVIOR_CHANGE。
优化模式 level 事件表示拓扑分组的开始/完成，组之间可能重叠；worker 事件保留名称并增加排队/复用事件。
新模式总耗时/调用次数等是可配置执行上限，不是吞吐/延迟性能承诺。真实模型成本、p95/p99、生产故障恢复均未实测。
