# S6 节点持久恢复：条件设计

状态：CONDITIONAL / 未实施。此前建议是长任务成本有证据后再做。当前轮内结果复用不持久化，进程崩溃后 inline 任务仍按既有 orphan 机制失败；独立只读 worker 仍可能整任务重复执行。

## 数据权威与契约

Java async-task-service 继续拥有任务、节点检查点和租约权威。不得把 Python Redis session 或本地文件变成第二任务权威，也不能把 AgentScope 状态作为公开存储格式。

后续中央契约需要版本化并同时支持旧 worker：检查点包含 task/plan revision、节点 ID、规范化输入摘要、依赖结果版本、服务端能力范围摘要、模型/提示词/工具版本、节点状态、尝试次数、结果引用与采集时间。身份/权限绑定 tenant+owner+scopes+department；不保存 JWT、确认 grant 或原始密钥。

节点写回与当前 lease owner/epoch、租约未过期检查在同一数据库事务执行；采用任务内节点唯一键和 revision 条件更新，检查影响行数。结果写入与节点事件 outbox 同事务，读取旧 epoch 的执行器不能提交成功。DDL 必须配套版本化迁移、表和字段注释。

## 恢复与副作用

- 无副作用、版本/输入/权限一致且在数据新鲜度范围内的成功节点可复用。
- RUNNING 节点可能已经调用模型或只读工具，允许重复成本；重新领取产生新 epoch。
- 写节点结果未知时进入待对账状态，不默认重放。必须通过原业务幂等键查询/对账确认效果，并重新验证用户权限与确认要求。
- 取消仅阻止后续动作，不撤销已提交效果。终态与 checkpoint 提交顺序需防止取消后迟到成功。
- 数据保留/删除范围覆盖结果对象、事件和备份；保留时长由真实业务敏感度确定，不能把本轮 TTL 当作持久保留要求。

## 启动此阶段的条件

1. 获得节点级恢复对延迟/重复模型成本的实际需求与可接受陈旧时间。
2. Java 中央任务服务所有者确认 API、DDL 与旧新 worker 共存方案，并授权相应仓库改动。
3. 有隔离的真实数据库/worker 环境，可验证领取后崩溃、结果落库前后崩溃、租约接管、旧 epoch 写入、取消竞争、权限撤销与版本变化。
4. 记录恢复耗时、重复调用及数据可用证据后再声明恢复能力。当前无 RTO/RPO 实测或承诺。

## 回滚

先扩展中央契约，再灰度只读节点恢复，最后评估写节点；旧 worker 不识别的新 kind 不得领取。关闭新分派并排空任务，保留检查点/事件用于排障；代码回退不等于撤销业务效果，不清表或重置历史。
