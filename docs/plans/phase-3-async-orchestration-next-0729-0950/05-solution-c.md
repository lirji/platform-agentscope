# 候选方案 C：Python 本地持久化任务账本 + 中央镜像

## 1. 方案定位

在 `agentscope-platform` 自建任务表与事件/outbox，以本地账本驱动执行、取消与 SSE，
再将状态镜像到 `async-task-service`。中央服务保留全平台可见性和 webhook，Python
本地库承担 Agent 任务的详细状态。

它与方案 A 的根本区别是形成“双账本”：Python 本地是执行源，中央是对外镜像。

## 2. 架构与模块职责

### Python 本地

- 新增关系型任务表、执行 attempt 表、事件表和中央同步 outbox。
- 提交事务一次写入任务与 outbox，然后本地 dispatcher 执行。
- 本地 SSE 从持久化事件表回放，天然可保存 DAG 细粒度进度。
- 中央同步器负责 create/update/cancel 对账。

### 中央服务

- 接收 Python 镜像状态，保留统一查询、租约和 webhook。
- orphan reaper 根据中央镜像判断异常，但需区分同步延迟和真实 orphan。

## 3. 核心流程

1. API 在本地事务创建任务与中央 create outbox。
2. 同步器创建中央任务并取得租约。
3. 本地执行器运行并写本地事件/终态，同时通过 outbox 更新中央。
4. 查询/取消可选择以本地为准或中央为准；SSE 读取本地事件。
5. 对账器修复两边状态差异。

## 4. 主要设计分叉

### 本地权威

查询返回本地状态，能保持详细事件，但违反“中央 async-task-service 为权威”的已确认基线。

### 中央权威

查询返回中央状态，则本地账本只是昂贵的缓存/outbox；取消、完成仍要解决双边先后次序，
而进程重启时仍缺少 token，不能真正恢复下游执行。

无论选择哪一支，都不能同时消除双写一致性和 token 生命周期问题。

## 5. 改动范围

- Python 新增数据库依赖、迁移框架、任务/事件/outbox repository、dispatcher、对账器。
- 当前仓库没有任务数据库基础设施；所有这些均为全新运维面。
- 中央需增加镜像幂等键、来源版本或 CAS 版本，避免旧消息覆盖新状态。
- 部署需提供 Python 数据库、迁移作业、备份、监控与清理。

## 6. 扩展性与实施成本

- 细粒度事件、查询和审计扩展灵活。
- 每个新 Agent 领域可写本地事件，但跨服务统一性变差。
- 实施与长期运维成本高于方案 A；价值与现有中央任务服务明显重叠。

## 7. 风险评审

### 兼容性

- 本地事件最容易复刻旧 DAG SSE。
- 两个查询源可能在同一时刻返回不同状态，旧客户端会观察到倒退或跳变。
- 中央 webhook 若使用镜像后的数据，时序可能晚于本地 SSE。

### 事务、并发与幂等

- 本地提交与中央 create 无法跨库原子提交，只能最终一致。
- outbox 可保证“最终尝试”，但需要中央幂等和版本检查。
- cancel 可能先写中央、后写本地，或反之；执行器必须同时检查两侧。
- 双写 terminal 的失败补偿和毒消息处理复杂。

### 性能

- 本地查询和 SSE 快，但增加数据库、dispatcher 和对账 I/O。
- 事件量需保留策略、索引与分页；否则任务表膨胀。

### 安全

- 本地任务表增加一份输入/结果/错误暴露面。
- 若为了恢复执行而保存 token，会直接违反约束；不保存 token 则持久化执行恢复收益有限。
- 两处 webhook/错误日志必须防止重复发送和敏感数据泄漏。

### 数据迁移

- 需要全新 schema、版本迁移、回填策略和清理作业。
- 未来移除本地账本还要做反向迁移，退出成本高。

### 灰度与回滚

- 双账本切换需要 shadow read 与持续对账。
- 回滚时必须确定哪边是最终状态，不能简单关闭 Python 数据库。
- 在途 outbox、中央已创建任务与本地未完成任务需人工/自动收敛。

## 8. 典型失败场景

- 本地事务成功、中央长期不可用：API 是否返回 202 与“中央先创建”要求冲突。
- 中央成功、本地 outbox ack 丢失：重复更新需要版本幂等。
- 两侧时钟或事件顺序不同导致状态回退。
- 本地数据库恢复后重放过期消息覆盖中央取消。
- 运维只清理一侧，造成孤立任务或 SSE 无历史。

## 9. 结论

本方案在细粒度 SSE 和本地审计上有优势，但与“中央服务权威、create+lease 后才 202”
直接冲突；同时无法在不保存 token 的前提下兑现可恢复执行。除非产品明确要把 Agent
任务拆成独立持久化域，否则不应为本期引入第二任务账本。
