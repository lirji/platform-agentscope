# 候选方案对比与裁决

## 1. 统一评价口径

评分为 1–5，**分数越高越好**。对“改动风险、复杂度、测试难度、回滚成本”而言，
5 分分别表示风险低、复杂度低、容易测试、回滚成本低。

权重：

| 维度 | 权重 | 评价问题 |
|---|---:|---|
| 正确性 | 25% | 能否满足 HTTP/JSON/SSE、租户、token、Process 只读与 orphan 收敛 |
| 改动风险 | 20% | 对现有同步路径、中央服务及其他 producer 的扰动是否可控 |
| 复杂度 | 10% | 状态、事务、部署和运维复杂度是否合理 |
| 可维护性 | 15% | 权威源、职责与故障定位是否清晰 |
| 扩展性 | 10% | 能否支持更多任务类型、水平扩容和可靠事件 |
| 测试难度 | 10% | 是否能以确定性 fixture 和故障注入覆盖 |
| 回滚成本 | 10% | 是否可按开关/路由回退且不需破坏性迁移 |

### 评分说明与反确认偏差检查

- A 得分最高不是因为它“最先进”，而是它最贴合现有交付基线且不引入第二权威源；
  它对严格 DAG SSE 与进程恢复确有不足，不能用高总分掩盖。
- B 的恢复与扩容能力最好，但当前认证模型没有安全地重建调用者身份的能力；把该能力
  写成“以后补”会使方案在安全上不可实施。
- C 能快速拥有本地事件历史，但重复建设中央任务能力，并把故障从单点变成双写一致性；
  其低分来自硬约束冲突，不是单纯因为改动大。
- D 在严格 SSE 正确性上最高，也对未来最有价值；低于 A 是因为它新增中央事件平台、
  数据表和事务路径，交付风险真实存在。
- 权重若将“严格旧 DAG SSE”视为一票否决而非普通正确性子项，A 不能直接入选，
  必须吸收 D 的持久事件能力。这正是最终裁决采用组合方案的原因。

## 5. 最终裁决

最终方案不是机械选择 A，而是：

1. 以 A 的“进程内执行器 + 中央权威状态 + token 内存限定 + kind 白名单 reaper”
   作为执行骨架；
2. 吸收 D 的“中央持久化事件日志、幂等 append、可靠回放”以满足旧 DAG SSE；
3. 不吸收 B 的拉取/重领，因为当前没有符合约束的委托身份机制；
4. 不吸收 C 的本地账本，避免双权威和额外数据库。

该组合比纯 A 多出中央事件表与 DAG progress sink，是为满足用户明确要求的旧 SSE
兼容而承担的有意识成本。实施必须通过 feature flag 分步开启：先状态和租约，再事件
双写校验，最后切换 SSE 读取；任一阶段均可关闭新异步入口而不影响现有同步端点。

## 6. 最终方案已知弱点

- 仍不支持跨进程恢复执行；崩溃任务会失败而非续跑。
- 任务最大运行时间受原始 JWT 剩余有效期限制。若业务需要更长任务，必须另立委托身份
  项目，不能在本期偷存 token。
- 中央事件日志扩大了 Java 服务与数据库改动面，性能和迁移成为关键路径。
- 中央现有 HTTP webhook outbox 是提交后监听器入队，不与 terminal update 严格同事务；
  最终方案会将 Agent kind 的 enqueue 纳入 store 事务或在无法统一时以发布阻断项处理。
- 模型输出具有非确定性，双跑不能要求字节级相等，必须用结构、停止原因和评测阈值。

## 7. 实施审批关卡

本文件与 `FINAL_PLAN.md` 仅形成实施输入，不授权改代码。批准前需明确接受：

- 新增中央事件表与 append API 是保持旧 DAG SSE 的必要范围；
- 长任务受 token TTL 限制，超限任务将失败而非刷新/持久化 token；
- 崩溃后不恢复推理，只由 orphan reaper 终结；
- orphan allowlist 永不包含旧 `agent.task` 和 workflow kind；
- 先影子/灰度验证，未通过双跑门禁前不切换生产 `AGENT_URI`。
